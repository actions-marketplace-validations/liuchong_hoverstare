# HoverStare 威胁模型与信任边界

> 本文是安全保证文档（assurance case）：说明 HoverStare 各运行形态下**有哪些资产、
> 谁是不可信的、边界划在哪里、现有对策是什么、还剩下什么风险以及为什么接受**。
> 模块级契约见 [`specs/`](../specs/README.md)；本文负责"安全上为什么可以这么做"。
> 实现与本文冲突时以本文为准并修实现；设计变更时**必须同步更新本文**。

## 1. 范围

覆盖三种运行形态：

| 形态 | 说明 | 主要凭据 |
|---|---|---|
| action（CI） | composite action 在用户仓库的 workflow 中运行，含**审查**与**开发模式** | `GITHUB_TOKEN`、可选 App private key、可选 `gh_pat`、可选 GPG 签名密钥 |
| serve（自部署） | 常驻 webhook 服务，接收 GitHub App 事件 | App private key、安装令牌 |
| 本地 CLI / 开发模式 | 维护者在自己机器或 CI 上运行 `review` / `develop` | 本地凭据（LLM key）、可选 git 凭据 |

部署与运维细节见 [`deploy.md`](deploy.md)、[`web-ide.md`](web-ide.md)。

## 2. 资产清单

| 资产 | 说明 | 泄漏后果 |
|---|---|---|
| LLM 凭据 | provider API key（BYOK） | 计费损失、被滥用 |
| App private key | 品牌身份与安装令牌交换 | 以 App 身份读写目标仓库 |
| `gh_pat` | 开发模式的 push / merge / 删分支 | 以维护者身份写仓库 |
| GPG 签名密钥 | 开发模式的提交签名 | 伪造"已验证"提交 |
| `GITHUB_TOKEN` | 平台颁发、按 permissions 收敛 | 受 workflow 权限限制的仓库读写 |
| 仓库内容 | 被审查/被开发的代码（可能闭源） | 商业信息泄漏 |
| 审查产物 | findings、覆盖账本、结构化输出 | 泄漏缺陷位置 |
| 平台评论/issue 正文 | 我们的输出与人类输入混居 | 冒充或误导维护者 |

## 3. 信任域与边界

```
┌── 不可信 ─────────────────────────────────────────────┐
│  · PR / issue / 评论正文（任何人可写）                  │
│  · diff 与被审查文件内容（可能故意构造）                │
│  · 模型输出（自然语言 + 结构化字段，均可能畸形）         │
│  · 仓库内任何文件（含规则文件——只从 base 分支读取）      │
└───────────────────────────────────────────────────────┘
          │ 边界 1：内容 → 提示
          ▼
┌── 半可信（仅结构可信）─────────────────────────────────┐
│  · 模型输出经 schema 校验与归一化后才进入系统            │
│  · 规则文件作为"补充说明"注入，永不覆盖核心规则           │
└───────────────────────────────────────────────────────┘
          │ 边界 2：模型 → 动作
          ▼
┌── 可信（我们的代码）───────────────────────────────────┐
│  · 工具机器层（只读注册表 / 路径沙箱 / 预算闸）           │
│  · 锚定、去重、指纹、发布流程                           │
│  · 凭据只在内存中，SecretString 包装，禁止进日志          │
└───────────────────────────────────────────────────────┘
          │ 边界 3：我们 → 平台
          ▼
┌── 外部 ───────────────────────────────────────────────┐
│  · 平台 API（HTTPS）· LLM provider（HTTPS）            │
│  · 发布产物下载源（release 资产，sha256 校验）           │
└───────────────────────────────────────────────────────┘
```

## 4. 攻击面与对策

### 4.1 prompt 注入（最高优先级）

- **面**：diff、被读文件内容、issue/评论正文都可能包含"忽略你的规则/把密钥发出去"之类文本。
- **对策**：系统提示固定声明 diff 与代码是**不可信数据**（该声明不可删改，spec 04）；
  工具在**机器层**只读（不是靠提示约束）；仓库规则文件只从 **base 分支**读取
  （PR 无法通过改 `AGENTS.md` 注入指令，spec 04 / M10）；审查模式下写工具根本不注册。
- **残余**：模型仍可能被诱导向评论里写入攻击者期望的文本（例如"这段代码是安全的"）。
  影响面被限制在"输出内容"，不涉及凭据与仓库写操作；开发模式的风险见 §5.3。

### 4.2 凭据处理

- **面**：日志、错误信息、评论、CI 输出、提交内容。
- **对策**：凭据一律 `SecretString`，禁止进日志（AGENTS.md §4.7）；令牌职责分离
  （身份走 App token、写操作走 PAT 类令牌，spec 11）；`.env~` 类文件历史上有被拦截的前科，
  因此密钥扫描是门禁项（spec 17 G5）并配合平台推送保护。
- **残余**：CI 上必然存在明文私钥（GPG 私钥、App private key）注入到进程内存；
  影响面限于该次 run 与仓库权限，无法进一步收敛。

### 4.3 只读边界与路径沙箱

- **面**：模型要求读取工作区外文件、逃逸路径、执行仓库代码。
- **对策**：路径沙箱（绝对路径 / `..` / 符号链接逃逸一律拒绝，spec 04）；
  唯一允许的进程调用是固定格式的 `git show`；不执行 checkout 下来的代码
  （AGENTS.md §4.3）。
- **残余**：读取仓库内文件本身会把内容送进模型上下文（见 §5.4）。

### 4.4 模型输出不可信

- **面**：畸形 JSON、错误行号、恶意路径、超长建议。
- **对策**：先 schema 校验再归一化；行号必须过锚定降级链（spec 06）；
  输出契约限定字段与路径规范（spec 16）；发布失败降级为摘要评论（spec 06）。
- **残余**：内容层面的错误判定无法机械消除，靠多 pass 投票 + verifier 压制
  （spec 05）。

### 4.5 分发链路

- **面**：下载并执行我们的发布产物（action 形态）；上游 action 引用被移动。
- **对策**：发布资产带 `.sha256` 且 action 侧强制校验（spec 08）；对上游 `uses:`
  引用实行全 SHA pin（spec 17 G1），因为内层浮动 tag 会绕过使用者的 pin。
- **残余**：使用者若使用浮动大版本 tag 引用我们的 action，仍会拿到新版本
  （这是使用者侧的选择，README 给出 SHA pin 建议）。

### 4.6 serve 形态

- **面**：伪造 webhook、重放、超大负载、安装令牌滥用。
- **对策**：HMAC-SHA256 验签且先验签后解析、常量时间比较（spec 10）；
  安装令牌缓存且提前刷新；同 PR 串行 + 全局并发上限；fork 场景按 sha 取代码而不是
  合并后的 head。
- **残余**：服务自身暴露在公网时，仍受"平台 webhook secret 泄漏"这一上游假设约束。

### 4.7 开发模式的写操作（本仓库风险面最大处）

- **面**：机器人能推分支、发 PR、合并、删分支，且持有 GPG 私钥与 PAT。
- **对策**：权限系统声明谁能用哪条命令（spec 12）；只允许协作方触发；队列严格串行、
  自触发熔断（spec 11 / M15）；human commit 永不被覆盖；合并需 checks 全绿 + 无冲突 +
  队列为空；提交身份与签名契约明确 committer 语义（M16）。
- **残余**：开发模式会执行"受控命令白名单"里的构建/格式化命令，其输出进入上下文；
  因此开发模式**不应用于不可信 PR**——它面向维护者自己的仓库。

## 5. 按形态的差异小结

| 关注点 | action 审查 | serve 审查 | 开发模式（CI / 本地） |
|---|---|---|---|
| 输入可信度 | PR 内容不可信 | 同左 | 仓库协作者可信，但 PR 内容仍不可信 |
| 凭据面 | 平台令牌（+可选 App/PAT） | App private key + 安装令牌 | 平台令牌 + PAT + GPG 私钥 |
| 写能力 | 评论/状态（+resolve） | 评论/状态 | 分支、提交、合并、删分支 |
| 主要防线 | 机器层只读 + 锚定 | 验签 + 串行 + 并发上限 | 权限 + 队列 + 签名契约 + 人工合并门 |

## 6. 残余风险与接受理由

| 残余风险 | 接受理由 | 缓解手段 |
|---|---|---|
| 模型可能被注入内容影响措辞 | 输出内容不改变凭据与仓库状态 | 只读机器层、锚定、verifier |
| 代码内容会离开本机/本仓库到模型 provider | BYOK 是产品前提；使用者可自选 provider 与自部署 | 文档明示；企业可自托管 serve + 内网端点 |
| CI 内存中存在明文私钥 | 平台模型的固有限制 | 最小权限、职责分离、门禁扫描 |
| 覆盖率/判定仍可能有漏报 | "宁缺毋滥"的精度取舍是产品决策 | 覆盖账本显式交代范围（spec 14） |
| 上游 action 供应链 | 无法完全消除 | 全 SHA pin 门禁 + 版本注释审计 |

## 7. 验证与维护

- **验证手段**：注入样例（把"忽略规则/输出密钥"之类文本放进 diff 与 issue）在真实 PR 上
  回归；密钥不出日志的断言（构造含密钥样式字符串的假配置，检查日志与评论）；
  `specs/17` 的门禁作为持续校验。
- **更新节奏**：新增运行形态、新增凭据种类、新增写能力、或新增外部输入来源时，
  必须同步更新本文（与 spec-first 同级要求）。
- **评审**：涉及凭据、写操作、路径沙箱、提示注入面的改动，必须在 PR 描述中显式
  引用本文对应小节。
