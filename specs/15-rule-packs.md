# 15 — 语言规则包（rule packs）

## 目标

让审查注意力按**文件是什么**聚焦：每份改动只注入"与它相关的检查要点"，而不是把所有
通用提醒一次性塞进系统提示。

本 spec 定义规则包的数据形态、匹配解析、注入契约与自检命令。

## 事实与边界

- 规则包**随二进制内置发布**（编译进产物），v1 不读工作区文件、不读远程配置，
  因此不构成新的外部输入面，也不是"仓库指令"的替代品。
- 规则包是**检查要点**，不是可执行策略：既不能覆盖核心规则（spec 04 的不可覆盖清单），
  也不能覆盖仓库指令（spec 04 §repo-instructions，base 分支读取）。
- 规则包只影响"看什么"，不影响输出契约（JSON-only，spec 04）、锚定（spec 06）、
  投票（spec 05）或覆盖记账（spec 14）。
- 规则包不引入新的工具与进程调用（不执行工作区代码）。

## 1. 与现有规则层次的关系

| 层 | 来源 | 权威 | 注入位置 |
|---|---|---|---|
| 核心规则 | 二进制内建 | 不可覆盖 | 系统提示固定段 |
| 仓库指令 | base 分支的规则文件（spec 04 / M10） | 高于规则包，低于核心规则 | `[REPOSITORY INSTRUCTIONS]` |
| **语言规则包** | 二进制内置，按路径命中（本 spec） | 检查要点 | `[LANGUAGE RULES]`（新段） |
| 内建默认 | 二进制内建 | 兜底 | 无命中包时使用 |

冲突时以核心规则 > 仓库指令 > 规则包 为准；规则包文本中不得出现"忽略前述规则"
"覆盖系统提示"之类的指令性表述（属评审拒绝项）。

## 2. 规则包结构

数据文件（随二进制内置）：

```
RulePack {
  id           // 稳定标识，如 "rust"、"ts-js"、"ci-yaml"
  version      // 包版本，随内容变更递增
  scope        // 匹配模式列表（路径 glob，按声明顺序）
  language     // 人类可读的语言/生态名（用于日志与 rules check 输出）
  checks[]     // 检查要点（分节：必须核对的契约 / 常见缺陷形态 / 勿报清单）
  examples     // 正例与反例各 ≥1 条（供离线评测与评审使用，不进入 prompt）
}
```

`examples` **不进 prompt**：它只用于离线评测与人审，避免把答案写进上下文。

## 3. 匹配解析

```
resolve(path, packs) -> RuleHit { pack, matched_pattern } | none
```

- 路径先规范化（仓库相对、正斜杠）再匹配；`scope` 按声明顺序 **first match wins**；
- **歧义消解**：仅针对已知的扩展名冲突集合，读取文件开头有限字节做内容嗅探；
  嗅探失败（超时/读不到）一律回退到声明顺序的命中结果，并把"回退"写进日志
  （不得静默改变行为）；
- **多包命中**：同一文件命中多包时，按"专指性（更长/更具体模式优先）→ 声明顺序"
  取最多 `max_rule_packs`（默认 2）份；被丢弃的命中记日志；
- 无命中的文件使用全局默认包（`default`）。

## 4. 注入契约

- 只注入命中该文件的那一份（加上被允许的第二份），总量有字节上限
  （沿用仓库指令的截断风格：单包与总量各有上限，超限截断并显式标记）；
- 段标题固定 `[LANGUAGE RULES]`，并声明"以下为检查要点，与核心规则冲突时以核心规则为准"；
- 规则包文本按**说明性材料**注入，不作为指令执行（与"diff/代码是不可信数据"的声明分开表述）；
- 同一 run 内多个 unit 命中不同包时，各自注入自己那一份，互不串味。

## 5. 自检命令

```
hoverstare rules list                 # 列出内置包（id/version/scope 摘要）
hoverstare rules check <path>         # 显示该路径命中的包、匹配模式、是否发生嗅探回退
```

`rules check` 是只读命令：不发模型调用、不写 GitHub、不需要凭据。

## 6. 与多 pass 的关系

规则包与 pass 视角**正交**：三路 pass（正确性 / 并发 / 安全）各自独立，命中的语言规则包
叠加在每一路上。不得把"语言规则"做成第四路 pass——那会改变投票语义。

## 7. 初始范围与扩张准则

v1 初始包（与项目自身技术面一致）：

| 包 | 覆盖 |
|---|---|
| `rust` | Rust 源码与 `Cargo.toml` |
| `go` | Go 源码 |
| `ts-js` | TypeScript / JavaScript（含 JSX 族） |
| `python` | Python |
| `ci-yaml` | CI 工作流与部署描述文件（路径模式限定） |
| `default` | 兜底通用检查要点 |

扩张准则（同时满足才收）：① 有明确的语言/生态边界；② 附带正反样例；
③ 能在离线评测里看出"加入该包后精度变化"，否则不上。

## 8. 配置

| 配置 | 默认 | 说明 |
|---|---|---|
| `rule_packs` | `true` | 关闭后只用仓库指令 + 内建默认 |
| `max_rule_packs` | `2` | 同一文件最多注入的包数 |

## 9. 可观测性

- `rule_resolved`：path、pack id、matched_pattern、是否嗅探回退；
- `rule_injected`：注入字节数、是否截断；
- `rules check` 的输出即为可解释性的用户入口。

## 10. 非目标

- 不做用户自定义规则包的分发/商店（v1 只内置）；
- 不做跨文件/跨模块的全局规则（那是仓库指令的职责）；
- 不把规则包变成硬门禁（它只影响提示，判定仍在 findings 与投票）。

## 11. 测试要点

- 每个内置包的 schema 校验单测（id/version/scope/checks/examples 齐备、无指令性文本）；
- 匹配解析：first match wins、专指性排序、多包上限、无命中走 default；
- 嗅探：命中冲突扩展名时按内容选定；读失败时回退且日志可见；
- 注入：字节上限与截断标记；`[LANGUAGE RULES]` 段落存在且不影响 JSON-only 契约；
- `rules check` 的只读性（无 provider 调用、无 GitHub 调用）。

## 12. 验收

- `hoverstare rules check src/main.rs` 输出命中的 `rust` 包与匹配模式；
- 真实 PR 上 logs 可见 `rule_resolved` / `rule_injected`，且注入总量在配置上限内；
- 关闭 `rule_packs` 后行为回到"仓库指令 + 默认包"；
- 单测覆盖 §11 全部条目，`cargo test --workspace` / clippy / fmt 全绿。
