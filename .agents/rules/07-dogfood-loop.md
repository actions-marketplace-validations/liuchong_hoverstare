# 07 — dogfood 驱动开发（用真实使用发现并修产品）

本项目用自己审查自己、用自己开发自己（dogfood）。这不是演示，而是主要的验证手段：
**产品在哪里不好用，就在哪里暴露缺陷**。本规则定义"边推进任务、边把工具修好"的工作方法。

## 1. 标准循环

1. 开 issue（含设计与约束）→ `@hoverstare` 方案轮 → 人确认 → `@hoverstare go` 建分支开 PR；
2. PR 上按**小任务**逐轮下发指令（一轮一件事、给文件位置与判据、禁止扩大范围）；
3. 每轮结束人做两件事：`cargo fmt`（bot 不能执行任何命令）与读取该轮报告；
4. CI 是本轮唯一客观反馈：红了就把**原始错误文本**贴回评论，让 bot 自己改；
5. 完成一个可独立验收的切片后评审并合并，未完成项留成下一步任务。

## 2. 核心原则：dogfood 不好用就是产品缺陷

推进任务时，**遇到下列任一情况必须立刻停下推进，先修产品，再回来推进**：

- **静默失败**：没有 CI、没有评论、没有报错，但事情没发生（例：PR 冲突时 GitHub 不跑
  `pull_request` check，CI 直接消失）；
- **空转**：轮次烧完全部预算却没有改动；自触发轮没有任务内容可依（例：模型去读
  `.git/refs`、去盘点整个仓库）；
- **指令不生效**：路由/解析把人的指令吃掉或当成别的命令（例：指令里在反引号中引用了
  命令写法，第一个匹配被当成命令）；
- **输出污染**：模型把工具调用写进正文、实验标记（`ZZZ` 之类）进了提交、标记泄漏到
  人类阅读的位置；
- **必然失败**：预算/额度/超时设置让某类任务注定做不成（例：思考模型的推理 token 计入
  输出额度，写死小值必然返回空正文）；
- **需要人做机械重复动作**：每轮都要人手动处理同一件本该自动的事。

判据是"这件事会不会让人类的真实使用变差或卡住"，而不是"它是否违反某条既有实现"。

## 3. 修复要求

1. 按 spec-first：先改 spec/规则，再改实现；能写成机器层约束的，不要只写在提示词里；
2. 必须带确定性测试（不需要真实 provider），并说明该测试钉住的正是这次暴露的失败；
3. 在 `AGENTS.md §7 运维经验` 与本规则中记录**真实证据**（run/评论链接、原始日志片段），
   让下一个人能复现；
4. 修完**回到原任务继续推进**，并在下一轮报告里说明"这一轮暴露/修掉了什么"。

## 3.5 已归档的实战案例

- **冲突静默掐掉 CI**：分支落后于 base → PR 冲突 → GitHub 不跑任何 `pull_request` check。
  修复：开发轮先 merge base（harness 侧），冲突则 abort 并回帖请人解决（`AGENTS.md §7`）。
- **合并提交缺身份**：本地能过、CI 挂（runner 没有全局 git 配置）。修复：merge 自带身份；
  验证方式是把全局 git 配置清空跑全套（`GIT_CONFIG_GLOBAL=/dev/null`）。
- **解析依赖外部工具与环境**：版本 pin 的标记用 `grep -i` 解析，在 runner 上没匹配到（本地同样
  输入能匹配）。修复：改成纯 bash 解析并自报结果（`pin scan: … resolved=[…]`），同时"取最后一个
  标记"。教训：**harness 的解析不要依赖 grep/sed 的 locale 行为**。
- **命令解析吞掉指令**：`strip_code_blocks` 靠反引号配对翻转，落单反引号会吞掉其后全文；
  且取"第一个"提及而非最后一个。已作为任务交给 dogfood 修（含单测）。

## 4. 与"人的机械活"的界线

- **设计内分工**（不要当成缺陷）：`cargo fmt`、解决 master 与分支的冲突、清理 bot 留下的
  实验痕迹、批准 Actions 的黄条；
- **产品缺陷**（要修）：上面第 2 节列出的所有情况；尤其是那些"本该由 harness 自动完成，
  却每轮都要人重做"的动作（冲突同步就是例子：bot 自己不会 rebase，也不该让模型去 rebase）。
